Protocol plugins live outside the tower

A Protocol Compatibility Plugin is an optional external process that implements one exact external protocol contract and maps it to the Native Station Contract. The Station Core remains complete and useful when every plugin is absent.

The external-process model

Each plugin is separately built, packaged, configured, supervised, versioned, released, supported, and operated, with its own listener, protocol code, optional bounded state, resource budget, metrics, and tests. The Core never discovers, loads, embeds, or supervises plugins; a deployment supervisor owns each plugin process, and the plugin connects as an ordinary scoped native caller.

  • Core never scans for or loads plugin code, hosts an in-process extension API, registers external protocol names, supervises plugin processes, or stores plugin-specific state.
  • Adding, removing, crashing, saturating, upgrading, rolling back, or retiring one plugin cannot change the Core artifact, the native contract, the persisted schema, or another plugin.
  • A plugin requirement cannot widen the native contract unless the capability independently serves direct native clients and passes Core acceptance.
  • If a protocol feature cannot map safely to the fixed native contract, the plugin owns the missing behavior or rejects support — it cannot make Core protocol-aware.

The LicoArc plugin, in both repositories

In the Go repository, an exact LicoArc Candidate adapter exists as separately built, quarantined candidate source: one process (badtower-licoarc-candidate) that pins one Candidate Protocol Line and transport digest, accepts only HTTP/2 over TLS 1.3 with deterministic closed-CBOR control maps and unchanged raw protected-packet bodies, and maps AFFILIATE, RESERVE, SUBMIT, RETRIEVE, CLAIM, and SETTLE through one scoped native gRPC caller. Its state, signer, configuration, and package are its own.

In BadTower.js, the licoarc.mailbox.v1 WebSocket listener is a replaceable compatibility plugin: it owns its route, subprotocol check, canonical CBOR frame codec, Ed25519 device-key handshake, and close codes, and drives the core store API without reaching beneath it.

BadTower alone owns any LicoArc adaptation it admits. LicoArc develops and verifies its Protocol Layer independently and owes BadTower no adapter, fixture, test, package, release, support, runner, or receipt.

Neither LicoArc surface is production-admitted today: the Go adapter waits on the open Native Excellence Gate, and the BadTower.js listener ships inside a pre-1.0 preview.

A2A, ACP, and MCP are plans, not features

The approved optional plugin plan set names a BadTower-owned LicoArc plugin, an A2A plugin, an independently admitted ACP plugin, and an MCP plugin. A2A and ACP remain distinct plugins even though the ACP project has joined A2A: no shared process, listener, configuration, state, adapter, alias, migration, or lifecycle. All three are deferred and not implemented in the Go repository.

Cross-protocol translation is rejected

No implicit translation or shared protocol state belongs in the Core or between plugins. Each admitted plugin maps exactly one pinned external contract; there is no generic protocol bridge.
