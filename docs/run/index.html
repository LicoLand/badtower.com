Two ways to run a Station

BadTower.js deploys a permanent-mailbox Station on Cloudflare Workers or a self-hosted container. The Go repository builds a native Station service around a strict configuration file. Both keep private operator material outside the repository.

BadTower.js on Cloudflare Workers

Deploy with three steps:

npm ci
          npm run station -- init --dir <private-dir>
          npm run station -- cloudflare-deploy --dir <private-dir> [--domain <name>]

init creates the 32-byte station key and .dev.vars in your private directory; cloudflare-deploy uploads that key as the BADTOWER_STATION_KEY secret and deploys the Worker in one step, using your existing wrangler login. A Deploy to Cloudflare Workers button offers the same flow and requires the same secret.

Self-hosted is a container path: docker-deploy builds the image on the operator machine for the remote daemon's architecture, streams it over SSH, and runs docker compose up with only compose file, a generated .env, and the secrets — the remote needs Docker only.

The station operator commands

CommandWhat it does
initCreates station.key (32-byte base64url, mode 0600) and .dev.vars; refuses to overwrite.
inviteMints a random mailbox id and a btm1 credential bound to it; --bind-within caps only the first binding.
revokeSends an offline-HMAC revocation body to /v1/revoke: packets are deleted and the mailbox can never bind again.
tlsCreates a private CA and server certificate under <dir>/tls/ for self-hosted HTTPS.
cloudflare-deployDeploys the Worker, uploading secrets from file rather than argv.
docker-deployBuilds, streams, and starts the self-hosted container on a remote Docker host.
healthChecks a Station's health endpoint.

All privileged material lives in a private directory passed with --dir; nothing private is tracked in the repository.

The Go Station binary

The BadTower repository builds a native Station service declared by one strict badtower.station.config.v1 file: namespace credentials, transport, health, and metrics listeners. Configuration is explicit, bounded, and fail closed — unknown fields, retired data roots, and non-loopback listeners without explicit allowance stop startup. Credentials are never accepted from argv or environment variables, and loopback listeners with Unix socket transport are the default, so a fresh build cannot expose itself publicly by accident.

Setup and operator commands — configuration validation, credential generation, and the RPC harness — are documented in the BadTower repository.

Production operation is the operator's own work: TLS certificates, access controls, process supervision, backups, and resource isolation are not supplied by either repository. No named hosted Station is claimed to be operating.

Verifying the source

The Go repository's routine closure is go test -race ./..., go vet ./..., go build ./..., and a clean gofmt -l. BadTower.js runs npm run check: typecheck, script lint, generated-type check, vitest, and a wrangler dry-run.
